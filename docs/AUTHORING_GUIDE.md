# Authoring Guide (read before writing any chapter)

This repository holds the manuscript and the runnable code for the course defined in
`COURSE_OUTLINE.md`. Every chapter has **one manuscript file** and **one code folder**.

## 2. Code rules

- **Python 3.10+ portable.** Anything needing 3.11+ must be flagged in a comment and the manuscript
  (the venv runs 3.13, so it will still execute).
- **Allowed third-party packages:** `numpy`, `pandas`, `torch` (CPU), `pytest`. Nothing else.
  Chapters 1–32 and 44–48 use the **standard library only** unless the chapter is about a package.
- **No network, no API keys, no GPU.** LLM chapters use a deterministic mock LLM client written in the
  chapter's code.
- **Deterministic output.** Fix all random seeds; never print timings, memory addresses, absolute paths,
  `id()` values, or set iteration order. Print sorted results when order is not meaningful.
  If a demo measures speed, print a comparison like `fast is faster: True` — never raw numbers.
- Each run must finish in **< 20 seconds** on a laptop CPU.
- Read data via `Path(__file__).resolve().parent.parent / "data" / "file.csv"`.
- File-writing demos write only to a `tempfile.TemporaryDirectory()`.

### Exercise stub (`exercises/exKK_<name>.py`)
Same docstring (without the approach ladder's answers — keep "Hints" instead), same function
signatures with bodies `raise NotImplementedError("TODO")`, and the same `main()` so learners can run it.

Run tests: `.venv/Scripts/python -m pytest chapters/chNN_<slug>` (learners: set `TARGET=exercises`).

### Generating outputs
`.venv/Scripts/python tools/run_all.py --chapter NN` runs every solution, writes `outputs/*.txt`,
and exits non-zero on failure. **Every solution must pass, and every chapter's tests must pass.**

## 3. Manuscript rules (`manuscript/chNN_<slug>.md`)

The manuscript is the book text. It must be complete and self-contained — a reader without the code
folder should still learn everything. Cover **every numbered section in COURSE_OUTLINE.md for that
chapter**, using the same numbers as headings (`## 9.3 Two-sum family with hash maps`).

Each chapter contains, in order:

1. `# Chapter NN. <Title>` then a line with tier, tracks, estimated study time, prerequisites.
2. **Learning objectives** (3–5 bullets).
3. **Recognise it** box (for pattern chapters): signal words and constraints → this technique.
4. **Sections** NN.1 … NN.x, each with: explanation in plain language, why interviewers care,
   annotated code, output shown in a ```text block (copied from the real run), complexity, pitfalls.
   Use tables and ASCII diagrams where they help.
5. **Worked problems** with the approach ladder (brute → improved → optimal + "why move up a rung"),
   follow-up questions, edge-case checklist, common wrong-but-tempting solutions.
6. **Interviewer's view** — what the rubric rewards in this chapter.
7. **Exercises** table linking to `chapters/chNN_<slug>/` (id, title, tier, pattern).
8. **Checkpoint quiz** — 5 questions, answers in a collapsed `<details>` block.
9. **Summary card** — one-page bullet recap.

Depth target: see the per-chapter page budget in `docs/BOOK_PLAN.md` (whole book < 450 pages); every code block in the manuscript must be code
that actually ran (copy from solutions or run snippets) and every output block must be real output.

Tier tags: ★ Core, ◆ Extended, ○ Reference. Tracks: S, M, L.
Write original problem statements. Refer to well-known problems by name only; don't copy platform text.
Don't claim company-specific question frequency.
